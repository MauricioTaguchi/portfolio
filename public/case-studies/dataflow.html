The problem

Cleaning data is not only a sequence of successful operations. A request can be retried, a worker can disappear, and a dataset can change while an earlier job is still running. A useful interface must make current data, change history and failure boundaries understandable.

My contribution

This personal project connects a React workspace to a FastAPI backend, PostgreSQL metadata, Celery workers and Redis coordination. Its documented implementation covers imports, quality inspection, transformation previews, revision-aware changes and recovery. The project is separate from my professional work at FIPE.

Data correctness and visible limits

Scatter charts preserve numeric X/Y pairs, including repeated X values, and identify omitted rows. Pie charts accept additive sums or counts and retain the full total when grouping categories. Means, minima and maxima use bars, lines or a KPI; category averages are not added into a pie total. The workspace shows the metric, source unit, contributing rows and omissions. Chart limits and preview exports are labelled explicitly; CSV export preserves quoted text, commas and line breaks.

The backend adds bounded dataset previews and reports tied to a recorded dataset revision. Those server controls require the full platform and are not exercised by the hosted sample.

A reproducible decision

In the synthetic sales replay case, removing one duplicated record changes the leading channel from Retail to Online while preserving two legitimate repeat purchases. The known total changes from BRL 3,197.80 to BRL 2,297.90; one missing amount remains explicit. An executable command checks the transformation and both analytical engines.

A short evaluation journey

  1. Open the isolated demo and dismiss or follow the guided tour.
  2. Inspect the sample dataset and its missing or duplicated values.
  3. Preview a transformation before applying it.
  4. Inspect the resulting history and undo the demo change.
  5. Reload to confirm that the frontend demo does not persist dataset edits.

What the result demonstrates

The browser demo demonstrates the workspace and local user journey. The repository exposes the backend’s contracts and test procedures. Neither a frontend demo nor a list of test files establishes production reliability: live recovery requires the separate process-integration suite and disposable database/broker services.

Trade-offs and next engineering work

Local versioned files make development reproducible, but horizontally scaled production requires a shared runtime storage design. The project documents additional work for high availability, operational alert routing, formal service objectives and independent security review. No customer adoption, measured business savings or production service guarantee is claimed here.
