Undoing a transformation does not erase its history

A small example that separates content, revisions and operation receipts.

Maurício Taguchi · 3 November 2026 · English edition

In this articleTwo identitiesRevision sequenceExpected versionReceiptsReproduceDataFlow connectionProduction limitsLearning resources

Content and revision have different identities

Imagine a dataset starting at revision 1, receiving a transformation at revision 2 and then needing to be restored. Restoring the original content does not have to reset the revision number to 1. An alternative is to publish the restored content as revision 3.

This distinction answers two different questions: which bytes are active, and what sequence of operations took place? Two states can contain exactly the same bytes while occupying different positions in the history.

Scope: this article's code is an in-memory teaching model, separate from DataFlow's implementation. Its tests do not verify a database, queue, storage system or multiple processes.

A restoration that preserves history

OperationActive revisionContent
Initial load1original
Transformation2transformed
Restore the content of revision 13original

The revision advances even when the content becomes identical to an earlier state. We can therefore recognize that a restoration happened instead of representing the old state as though no operation had occurred.

In the example, Snapshot holds a revision and immutable bytes. A hash allows content comparison. It is not access control or a tamper-proof history: this is an in-memory structure with no protection against someone who controls the process.

The client's expectation belongs to the operation

An interface might still display revision 2 after another operation has published revision 3. A request based on that old screen should not silently overwrite a more recent change.

The example requires expected=2. When the current revision differs, it raises a conflict and preserves the state. This demonstrates a version check, not a concurrency solution: a real implementation must coordinate the check and publication atomically.

What happens when the operation succeeds but its response is lost?

The client may not know whether restoration completed. Blindly repeating the operation would be risky. The example therefore uses a request key and stores a receipt containing the previous revision, resulting revision and restored source.

Repeating the same key with the same arguments returns the captured receipt. Even if the dataset later reaches revision 4, that receipt still describes the operation that produced revision 3. It is not a read of the current state, and replay does not change the current head.

Reusing the key with different arguments is a conflict. Keys in this example belong to a single instance. Production also needs an explicit scope by resource, actor and action, with durable storage and authorization.

How this relates to DataFlow

DataFlow's receipt documentation describes a broader design: events and revision changes published within a PostgreSQL transaction, retained replay receipts and snapshot integrity checks. It also identifies limits, including database administrators' ability to bypass some protections.

That documentation is a reference for the project's design. The full DataFlow integration suite and process-failure simulations were not executed for this teaching article. This reduced model helps explain the invariants; it does not replace integration testing.

What production still requires

Durability, tenant isolation, transactions, locking, file corruption, snapshot expiration and recovery after failure are separate engineering problems. Each needs defined behavior and its own evidence.

Undoing a change should not erase evidence that it occurred. Separating content, revision and receipt makes that intent easier to explain, implement and test.
