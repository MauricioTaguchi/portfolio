Validate a CSV with Python before building a dashboard

Explicit input rules, reproducible diagnostics and an unchanged source file.

A readable file is not necessarily reliable data

A CSV may open successfully and still contain duplicate sales, impossible dates or missing amounts. Before building a dashboard, define what a valid record means. This tutorial provides a small, dependency-free Python validator that reports problems without rewriting the source.

All records in the example are synthetic. The aim is an inspectable quality check, not automatic correction or a claim that a file matches business reality.

Make the contract explicit

The exact header is sale_id,date,amount_brl, in that order. IDs are nonempty text and must be unique: leading zeroes are preserved. Dates must be real calendar dates in YYYY-MM-DD format. Amounts use plain decimal notation with up to two fractional digits and no currency symbol or thousands separator.

This example models positive, paid sales. Refunds, adjustments and free transactions need different rules. A tutorial rule is not automatically a production requirement.

Delimiter and decimal separator are not inferred. The defaults are comma-delimited fields and a dot decimal separator. Select semicolon and comma explicitly for a common Brazilian export format.

Run the example

Use Python 3.11 or later. Download these files into the same directory and open a terminal there. On Windows, py may be the available command instead of python. No third-party installation is required.

The valid fixture returns exit code 0. The problematic fixture returns 1 intentionally: it contains six records and five diagnostics. Both occurrences of the duplicated ID are flagged; the other diagnostics identify an impossible date, a missing amount and a negative amount. Exit code 2 means an operational problem, such as an unreadable input.

python validate_sales.py vendas.csv --delimiter ";" --decimal-separator ","

Interpret evidence carefully

valid is true only when inspection completed and no checked rule failed. complete: false means structural parsing or a limit prevented complete inspection. Do not treat a partially inspected file as approved.

record counts logical records excluding the header. line_end records the final physical line, which matters when quoted fields contain line breaks. The report omits raw field values, and the source is never rewritten. Duplicate handling does not silently choose a record to keep.

Implementation choices

The standard csv module keeps fields as strings, allowing explicit validation. The file is opened with newline="" and UTF-8 BOM handling. A strict date format check is followed by calendar validation.

Amounts first pass a restricted decimal syntax check, then become Decimal directly from text. There is no intermediate binary floating-point conversion. Nonfinite tokens, scientific notation and excess fractional digits fail this particular contract.

The implementation counts IDs before adding duplicate diagnostics, so every occurrence is flagged. Outer whitespace is ignored for validation only; leading zeroes remain significant. None of those decisions changes the input bytes.

Test the boundaries

The 30-test suite covers the happy path and boundary cases: leap days, malformed dates, column counts, quoted delimiters, multiline records, malformed CSV, encoding errors, command exit codes and refusal to overwrite the input. A hash comparison verifies source preservation.

All 30 tests passed locally with Python 3.13.5. That result describes this version and environment; rerun the suite after changes. Add a regression case before changing a business rule.

What this does not prove

The tutorial limits inputs to 10 MiB and 100,000 records and keeps IDs in memory. It is not a distributed ingestion engine, a hostile-file security boundary or a proof that a sale really happened. It does not reconcile totals or validate tax obligations.

A useful next step is to connect diagnostics to an explicit policy: reject the batch, ask the source owner to correct it or quarantine records for review. Validation produces evidence. The business process decides what happens next.
