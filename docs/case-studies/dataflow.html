The hosted frontend uses synthetic sample data and temporary, in-memory edits. It does not run the backend, verify durable recovery, or accept an API connection.

The problem

Cleaning data is not only a sequence of successful operations. A request can be retried, a worker can disappear, and a dataset can change while an earlier job is still running. A useful interface must make current data, change history and failure boundaries understandable.

My contribution

This personal project connects a React workspace to a FastAPI backend, PostgreSQL metadata, Celery workers and Redis coordination. Its documented implementation covers imports, quality inspection, transformation previews, revision-aware changes and recovery. The project is separate from my professional work at FIPE.

A short evaluation journey

  1. Open the isolated demo and dismiss or follow the guided tour.
  2. Inspect the sample dataset and its missing or duplicated values.
  3. Preview a transformation before applying it.
  4. Inspect the resulting history and undo the demo change.
  5. Reload to confirm that the frontend demo does not persist dataset edits.

What the result demonstrates

The browser demo demonstrates the workspace and local user journey. The repository exposes the backend’s contracts and test procedures. Neither a frontend demo nor a list of test files establishes production reliability: live recovery requires the separate process-integration suite and disposable database/broker services.

Trade-offs and next engineering work

Local versioned files make development reproducible, but horizontally scaled production requires a shared runtime storage design. The project documents additional work for high availability, telemetry, formal operating objectives and independent security review. No customer adoption, measured business savings or production service guarantee is claimed here.
