Como avaliar um SDK além do build

Instalação, fixtures e integração ao vivo: três verificações que não devem ser confundidas.

Maurício Taguchi · 3 de novembro de 2026

Neste artigoPrimeira execuçãoCamadas de evidênciaInstalaçãoTeste offlineTeste ao vivoManutençãoRoteiro de revisão

O início rápido também faz parte do produto

Um SDK pode compilar e ainda oferecer uma experiência confusa para quem começa. Um nome de pacote ainda não publicado, parâmetros genéricos ou a falta de distinção entre mock e API real podem interromper o primeiro uso antes que a pessoa consiga avaliar a biblioteca.

O exercício deste artigo usa o Frankfurter SDK, um cliente TypeScript não oficial. A proposta não é certificar a API nem reescrever o gerador: é criar um caminho pequeno e verificável entre o checkout do código e um primeiro exemplo compreensível.

Separe três tipos de evidência

VerificaçãoO que demonstraO que não demonstra
BuildO código compilou naquele ambiente.Que os exemplos ou a API funcionam.
Teste offlineO cliente se comporta como esperado com fixtures controladas.Disponibilidade ou contrato atual do serviço remoto.
Teste ao vivoA integração respondeu naquela execução.Garantia de disponibilidade futura.

Essas evidências se complementam. Usar uma delas como substituta das outras cria confiança sem sustentação. Também é importante separar resultados históricos de uma nova execução.

Não instrua uma instalação que não existe

O README do projeto informa que o pacote ainda não foi publicado no npm. Por isso, o guia complementar usa instalação a partir do código-fonte, com o arquivo de dependências travadas do repositório.

git clone https://github.com/MauricioTaguchi/frankfurter-sdk.git
cd frankfurter-sdk
npm ci --prefix ts
npm test --prefix ts

Use Node.js 24 para acompanhar o guia do projeto. O script pretest faz o build antes da suíte. Isso é diferente de regenerar o SDK: quem apenas deseja usá-lo não precisa reconstruir o modelo do gerador.

Um exemplo offline com uma hipótese clara

A hipótese é pequena: o mock começa vazio; depois de receber uma moeda sintética BRL, uma listagem devolve esse registro. O teste importa o SDK compilado real e substitui fetch por uma função que falha se for chamada. Assim, uma chamada inesperada à rede não passa despercebida por esse caminho.

const { FrankfurterSDK } = require('./ts/dist/FrankfurterSDK.js');

async function main() {
  const client = FrankfurterSDK.test({
    entity: { currency: { BRL: { id: 'BRL', code: 'BRL' } } },
  });
  const currencies = await client.Currency().list();
  console.log(currencies.map(currency => currency.data()));
}
main().catch(error => {
  console.error(error);
  process.exitCode = 1;
});

O registro é uma fixture. Não representa uma cotação e não demonstra que BRL apareceu em uma resposta ao vivo. A interceptação de fetch verifica o transporte utilizado neste exemplo; não é um isolamento de rede de todo o sistema operacional.

Teste a integração separadamente

O repositório já contém scripts/smoke-live.cjs. Ele faz leituras na API pública, compara uma taxa histórica com a listagem filtrada, consulta moedas e verifica uma resposta para moeda inválida.

node scripts/smoke-live.cjs

A data fixa no script é histórica: 2026-10-01. O teste não deve ser apresentado como consulta da cotação de hoje. Uma falha precisa ser analisada, não escondida desativando TLS ou trocando o comportamento esperado sem investigar.

Mantenha a melhoria no lugar certo

O diretório ts/ é saída gerada. Alterações manuais ali podem desaparecer na próxima geração. Por isso, o guia complementar e o novo teste ficam fora dessa árvore. Corrigir definitivamente os exemplos produzidos pelo gerador exige modificar o modelo, template ou componente responsável e regenerar.

A melhoria foi integrada ao projeto pela solicitação de alteração do início rápido. Ela inclui o guia, o script e uma verificação automática dedicada. Em 3 de novembro de 2026, a execução correspondente concluiu com sucesso a instalação, o build, a suíte existente e o novo exemplo offline.

git switch main
git pull --ff-only
npm ci --prefix ts
npm test --prefix ts
node scripts/quickstart-offline.cjs

Atualização de verificação — 3 de novembro de 2026: depois da primeira versão deste artigo, uma verificação separada com a API real concluiu com sucesso o build do SDK e a consulta histórica. O registro está em 4 de novembro no horário UTC e em 3 de novembro no horário de São Paulo.

O teste offline continua sendo evidência de comportamento com fixtures. A execução ao vivo é uma evidência adicional, limitada àquele momento; não garante disponibilidade futura. Consulte o histórico de verificação para não confundir registros antigos com novas execuções.

Um roteiro reutilizável de revisão

Comece em um ambiente limpo. Confira se o comando de instalação corresponde ao estado real do pacote. Execute o exemplo exatamente como escrito. Registre a versão, a entrada, a saída esperada e a falha observada. Acrescente um teste pequeno para impedir regressão e deixe explícito o que não foi verificado.

Documentação útil reduz a distância entre “há código no repositório” e “outra pessoa consegue usar e avaliar esse código”. Esse é um resultado concreto, mesmo quando a melhoria é pequena.
