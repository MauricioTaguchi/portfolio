Como validar um CSV com Python antes do dashboard

Um contrato explícito, diagnósticos reproduzíveis e nenhuma correção silenciosa do arquivo original.

Maurício Taguchi · 3 de novembro de 2026 · Read in English

Neste artigoO problemaContrato de entradaExecutarLer o relatórioImplementaçãoTestesLimitações

Abrir um arquivo não é validar os dados

Um CSV pode abrir normalmente no Excel e ainda conter problemas que distorcem uma análise. Uma venda repetida aumenta o faturamento; uma data impossível impede o agrupamento por mês; um valor vazio pode desaparecer silenciosamente de um cálculo. Antes do dashboard, precisamos decidir o que um registro válido significa.

Neste tutorial, vamos construir um validador pequeno, reproduzível e sem dependências externas. Ele lê um arquivo de vendas fictício, produz diagnósticos em JSON e preserva o original. O objetivo não é corrigir tudo automaticamente, mas tornar cada decisão de qualidade explícita.

Primeiro, um contrato de entrada

O arquivo terá exatamente três colunas, nesta ordem: sale_id, date e amount_brl. O identificador é texto: 0001 e 1 continuam diferentes. A data precisa existir no calendário e usar o formato YYYY-MM-DD. O valor aceita somente notação decimal simples, com até duas casas e sem símbolo monetário.

Regra de negócio, não verdade universal: este exemplo representa vendas pagas e exige valor positivo. Devoluções, ajustes e vendas gratuitas precisam de outro contrato. Não transforme uma regra do tutorial em requisito da sua empresa sem verificar o contexto.

Também não vamos adivinhar a localidade. Por padrão, o delimitador é vírgula e o separador decimal é ponto. Um CSV com ponto e vírgula e vírgula decimal exige opções explícitas. Assim, 1,234 não vira silenciosamente um número com significado diferente.

Baixe e execute o exemplo

Use Python 3.11 ou superior. Salve os arquivos abaixo na mesma pasta e abra um terminal nela. No Windows, substitua python por py caso esse seja o comando disponível. Não há bibliotecas adicionais para instalar.

Arquivos do tutorial

python -m unittest -v
python validate_sales.py sales_valid.csv
python validate_sales.py sales_invalid.csv --output report.json

O arquivo válido termina com código 0. O arquivo com problemas termina com código 1: isso é o comportamento esperado, não uma falha inesperada do programa. Código 2 indica problema operacional, como arquivo inexistente ou saída que tentaria sobrescrever a entrada.

Para outra convenção de CSV, forneça as duas escolhas:

python validate_sales.py vendas.csv --delimiter ";" --decimal-separator ","

O que o relatório realmente diz

A amostra problemática contém seis registros e produz cinco ocorrências de problemas. As duas ocorrências do ID 0002 são sinalizadas; além delas, há uma data impossível, um valor ausente e um valor negativo. Não escolhemos automaticamente qual duplicata manter.

CampoSignificado
validSó é verdadeiro quando a leitura foi completa e não houve problemas nas regras verificadas.
completeInforma se foi possível concluir a inspeção estrutural dentro dos limites.
recordPosição do registro, sem contar o cabeçalho.
line_endÚltima linha física do registro; campos entre aspas podem conter quebras de linha.

Esses detalhes evitam confundir uma linha física com um registro lógico ou tratar uma inspeção interrompida como aprovação. Um CSV malformado, por exemplo, produz complete: false. Corrija a estrutura e execute a verificação novamente antes de interpretar os demais resultados.

Decisões de implementação

O módulo csv lê os campos como texto; por isso a conversão e as regras ficam sob nosso controle. Abrimos o arquivo com newline="", como orienta a documentação, e usamos utf-8-sig para aceitar UTF-8 com ou sem marca inicial. A data passa por uma verificação de formato e pelo calendário real.

Para valores, primeiro restringimos a notação permitida. Depois usamos Decimal a partir do texto, sem conversão intermediária para float. Isso mantém explícito o tratamento decimal. Valores como NaN, Infinity, notação científica ou três casas decimais são rejeitados pelo contrato.

IDs repetidos são contados antes de produzir os diagnósticos de duplicidade. Dessa forma, todas as ocorrências são sinalizadas. Espaços externos são ignorados durante a comparação, mas os bytes do arquivo nunca são regravados. O relatório também não copia valores brutos dos registros.

Testar os limites, não apenas o caso feliz

A suíte contém 30 testes. Ela cobre datas impossíveis, ano bissexto, colunas extras, campos vazios, IDs com zeros, vírgulas entre aspas, registros com múltiplas linhas, arquivo malformado, codificação inválida e os códigos de saída. Um teste compara o hash da entrada antes e depois da execução para verificar que o original foi preservado.

Os 30 testes passaram no ambiente local com Python 3.13.5. Isso é evidência para esta versão do exemplo, não uma certificação de qualquer arquivo futuro. Execute a suíte de novo ao mudar uma regra e acrescente um caso que reproduza a necessidade.

O que fica fora deste tutorial

O exemplo limita o arquivo a 10 MiB e a 100.000 registros; os IDs ficam em memória. Não é um mecanismo de processamento distribuído nem uma proteção completa contra arquivos hostis. Também não confere se a venda aconteceu, se o valor concilia com o sistema de origem ou se existem requisitos fiscais adicionais.

O próximo passo prático não é apagar linhas automaticamente. É combinar o relatório com uma política: rejeitar a carga, pedir correção à origem ou separar os registros para revisão. A validação cria evidência; a decisão depende do negócio.
