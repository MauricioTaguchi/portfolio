How to evaluate an SDK beyond the build

Installation, fixtures and live integration: three checks that must not be confused.

Maurício Taguchi · 3 November 2026 · English edition

In this articleFirst runEvidence layersInstallationOffline checksLive integrationMaintenanceReview procedureLearning resources

The quickstart is part of the product

An SDK can compile and still be confusing to use. An unpublished package name, placeholder parameters or an unclear distinction between mocks and the real API can stop a first-time user before they can evaluate the library.

This article uses Frankfurter SDK, an unofficial TypeScript client. The goal is not to certify the API or rewrite the generator. It is to create a small, verifiable path from a source checkout to an understandable first example.

Separate three kinds of evidence

CheckWhat it demonstratesWhat it does not demonstrate
BuildThe code compiled in that environment.That examples or the API work.
Offline testClient behavior with controlled fixtures.Remote availability or the current service contract.
Live testThe integration responded during that execution.A guarantee of future availability.

These checks complement one another. Treating one as a replacement for the others creates unsupported confidence. Historical results must also be distinguished from a fresh execution.

Do not document an installation that does not exist

The project's README records that the package has not been published to npm. The companion guide therefore uses a source installation and the repository's committed lockfile.

git clone https://github.com/MauricioTaguchi/frankfurter-sdk.git
cd frankfurter-sdk
npm ci --prefix ts
npm test --prefix ts

Use Node.js 24 to follow the project guide. The pretest script builds the package before the suite. This is different from regenerating the SDK: someone who only wants to use it does not need to rebuild the generator's model.

An offline example with a clear hypothesis

The hypothesis is deliberately small: the mock starts empty; after seeding a synthetic BRL currency, listing currencies returns that record. The test imports the real compiled SDK and replaces fetch with a function that fails if called. An unexpected network request through that transport therefore cannot pass unnoticed.

const { FrankfurterSDK } = require('./ts/dist/FrankfurterSDK.js');

async function main() {
  const client = FrankfurterSDK.test({
    entity: { currency: { BRL: { id: 'BRL', code: 'BRL' } } },
  });
  const currencies = await client.Currency().list();
  console.log(currencies.map(currency => currency.data()));
}
main().catch(error => {
  console.error(error);
  process.exitCode = 1;
});

The record is a fixture, not an exchange rate or evidence that BRL appeared in a live response. Intercepting fetch checks the transport used in this example; it is not operating-system-wide network isolation.

Test the integration separately

The repository already contains scripts/smoke-live.cjs. It reads the public API, compares a historical rate with a filtered list, reads currencies and checks an invalid-currency response.

node scripts/smoke-live.cjs

The fixed date is historical: 2026-10-01. This is not a query for today's rate. Investigate failures rather than hiding them by disabling TLS or changing expectations without understanding the cause.

Keep the improvement in the right place

The ts/ directory is generated output. Manual edits there can disappear during regeneration. The companion guide and example check therefore live outside that tree. A lasting correction to generated examples would require changing the responsible model, template or component, followed by regeneration and testing.

The quickstart improvement was merged through the quickstart pull request. It includes the guide, script and dedicated workflow. The recorded offline run completed installation, build, the existing suite and the new example successfully.

git switch main
git pull --ff-only
npm ci --prefix ts
npm test --prefix ts
node scripts/quickstart-offline.cjs

Before updating an existing checkout, inspect git status and preserve local changes.

Verification update: a separate live API run subsequently completed the real SDK build and historical query successfully. That record is dated 4 November 2026 UTC, corresponding to 3 November in São Paulo.

The offline check remains fixture evidence. The live run is additional evidence for that execution only, not future availability. The verification history distinguishes the original observations from later runs. Translating this article does not constitute another live test.

A reusable review procedure

Start in a clean environment. Confirm that installation instructions match the package's actual distribution status. Run the example exactly as written. Record the version, input, expected output and observed failure. Add a small regression test and explain what was not verified.

Useful documentation closes the gap between code existing in a repository and another person being able to use and assess it. That is a concrete outcome, even when the improvement is small.
