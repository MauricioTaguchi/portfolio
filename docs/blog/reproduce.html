1. Extract the example package

Use Python 3.11 or later. Extract the ZIP into a new folder and open a terminal in that folder. Preserve its subdirectories: the runner needs both examples next to it. The teaching code uses only the Python standard library; no Node.js, Docker or API key is required.

Alternatively, obtain the repository and run the same examples under public/blog/exemplos/. Do not overwrite a checkout with uncommitted changes.

git clone https://github.com/MauricioTaguchi/portfolio.git
cd portfolio

2. Run tests and demonstrations

From the extracted examples package, on Windows:

py -B run_examples.py

On macOS or Linux:

python3 -B run_examples.py

From the repository root, use python -B public/blog/exemplos/run_examples.py instead. Replace python with the available launcher.

The runner executes both suites, demonstrates revision restoration, verifies fixture exit codes and compares the input files before and after. By default, it writes the report to a temporary directory and removes it on completion.

3. Inspect the result, not just the message

{
  "status": "passed",
  "valid_fixture_exit": 0,
  "invalid_fixture_exit": 1,
  "invalid_records": 6,
  "diagnostics": 5,
  "source_files_unchanged": true
}

There are 38 CSV tests and eight revision-model tests. Filesystem-link cases may be skipped on systems that do not permit creating links; read and report that count. A skipped test is not a passed test. Site-maintenance tests are a separate suite.

To keep the report, create a new directory and point the runner to it:

mkdir results-session-01
py -B run_examples.py --output-dir results-session-01

The report is results-session-01/invalid-report.json. Reusing that destination is refused to preserve the existing report. Choose a new directory rather than deleting evidence merely to make a command pass.

4. Preserve files instead of overwriting them

The validator creates reports exclusively. An existing file, hard link or symbolic link produces operational exit code 2. Comparing path strings alone was insufficient because different names can refer to the same file.

The regression tests reproduce that case with synthetic inputs. Exclusive creation prevents overwriting an existing destination, but it is not crash-safe atomic publication: an interrupted write may leave incomplete JSON. Check the command's result before consuming its output.

Reference: Python's exclusive file-creation mode.

5. Explain the demonstration in your own words

Show the problematic CSV, execute the runner, open the report and explain why six records produce five diagnostics. Then distinguish restoring content from replaying a request. The study guide and downloadable speaker script follow the slide deck.

Why are both duplicate occurrences flagged?

The file does not establish which occurrence should prevail. The validator flags both instead of silently choosing a sale to keep.

Why can exit code 1 be expected?

For the validator, it means the data violates a rule. Code 2 indicates an operational problem. The runner knows the invalid fixture should exit with 1 and verifies that expectation.

Should restoring revision 1 reset the counter to 1?

Not in this model. Old content becomes the content of a new revision, retaining evidence of the restoration. See the revisions article.

Does an offline check prove API availability?

No. A fixture checks controlled behavior. A live request tests another boundary at a particular time. See the SDK article.

What these resources do not establish

The records are synthetic. These examples do not run DataFlow's backend, certify real business data or guarantee Frankfurter API availability. They are deliberately small and bounded.

The slide deck and script are preparation materials. They do not document a delivered talk or workshop.
