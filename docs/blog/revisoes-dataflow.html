Desfazer uma transformação não é apagar o histórico

Um exemplo pequeno para separar conteúdo, revisão e recibos de operações.

O conteúdo e a revisão têm identidades diferentes

Imagine que um conjunto de dados começa na revisão 1, recebe uma transformação na revisão 2 e depois precisa ser restaurado. Recolocar o conteúdo original não precisa significar voltar o número da revisão para 1. Uma alternativa é publicar esse conteúdo como revisão 3.

Essa distinção permite responder a duas perguntas diferentes: “quais bytes estão ativos?” e “qual foi a sequência de operações?”. Dois estados podem conter exatamente os mesmos bytes e ainda ocupar momentos diferentes no histórico.

Escopo: o código deste artigo é um modelo didático em memória, separado da implementação do DataFlow. Os testes deste exemplo não demonstram o funcionamento de banco, fila, armazenamento ou múltiplos processos.

A revisão avança mesmo quando o conteúdo volta a ser igual. Isso permite reconhecer que a restauração aconteceu, sem apresentar o estado antigo como se nenhuma operação tivesse ocorrido.

No exemplo, Snapshot guarda uma revisão e bytes imutáveis. Um hash permite comparar o conteúdo. Ele não substitui controle de acesso nem torna o histórico inviolável: aqui existe apenas uma estrutura em memória, sem proteção contra alguém que controla o processo.

A expectativa do cliente faz parte da operação

Uma interface pode estar mostrando a revisão 2 quando outro processo já publicou a 3. Uma solicitação baseada naquela tela antiga não deveria sobrescrever uma mudança mais recente silenciosamente.

O exemplo exige expected=2. Se a revisão atual não for 2, lança um conflito e mantém o estado. É uma demonstração da checagem de versão, não uma solução de concorrência: uma implementação real precisa coordenar a checagem e a publicação de forma atômica.

E quando a operação funciona, mas a resposta se perde?

O cliente pode não saber se a restauração foi concluída. Reenviar cegamente a operação seria arriscado. Por isso o exemplo usa uma chave de solicitação e guarda um recibo com a revisão anterior, a nova revisão e a origem restaurada.

Repetir a mesma chave com os mesmos argumentos retorna o recibo capturado. Mesmo que o conjunto avance depois para a revisão 4, o recibo continua descrevendo a operação que produziu a 3. Ele não é uma leitura do estado atual.

Reutilizar a chave com argumentos diferentes é um conflito. No exemplo, as chaves existem dentro de uma única instância. Em produção, também é preciso definir escopo por recurso, usuário e ação, além de garantir persistência e autorização.

Reproduza a sequência

Modelo PythonOito testesInstruções

Salve os dois arquivos Python na mesma pasta. Use Python 3.11 ou superior e execute:

python -m unittest -v
python revision_demo.py

A saída observada no exemplo é:

Restored original content as revision 3; replay kept head at revision 4.

Os oito testes passaram localmente com Python 3.13.5. Verificam o avanço da revisão, a repetição do recibo, a preservação de uma alteração posterior, conflitos de chave e versão, alvo inexistente, chave vazia e igualdade de conteúdo entre revisões.

Como isso se relaciona com o DataFlow

A documentação de recibos do DataFlow descreve uma solução mais ampla: eventos e alterações de revisão publicados em transação no PostgreSQL, recibos retidos para repetição e checagens de integridade de snapshots. Ela também explicita limites, como a capacidade de administradores do banco de contornar certas proteções.

Essa documentação é a referência para entender a proposta do projeto. Neste artigo, não executei a suíte completa de integração do DataFlow nem simulei falhas de processos. O exemplo reduzido ajuda a explicar duas invariantes, mas não substitui essa verificação.

O que ainda precisa existir em produção

Persistência, isolamento entre usuários, transações, bloqueios, corrupção de arquivos, expiração de snapshots e recuperação após falhas são problemas separados. Cada um precisa de comportamento definido e evidência específica.

A conclusão é simples: desfazer uma mudança não deveria apagar a evidência de que ela existiu. Separar conteúdo, revisão e recibo torna essa intenção mais fácil de explicar, implementar e testar.
